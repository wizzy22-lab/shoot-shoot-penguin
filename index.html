Shoot Shoot Penguin
Design System

Shoot Shoot Penguin의 초기 화면을 검토하며, 반복 요소의 스타일과 색의 의미가 화면마다 달라지는 문제를 발견했습니다.
조작 요소와 경기 상태의 표현을 분리하고, 토큰과 컴포넌트를 정리해 두 사용자 화면에 적용할 공통 기준을 만들었습니다.

Reviewing the first screens of Shoot Shoot Penguin, I found that repeated elements were styled differently from screen to screen, and that colour meant something different in each one.
Separating how controls and game state are expressed, then settling the tokens and components, gave one standard both sides of the app could be built on.

이 케이스에서 볼 것What to look for

이 앱에서 색이 무슨 일을 해야 하는지 먼저 정했습니다. 기존 화면을 뜯어보니 같은 색이 버튼과 상태, 두 가지 뜻으로 쓰이고 있었습니다 — 브랜드 색을 빼야 하는 이유는 여기서 나왔습니다. 그리고 그 규칙을 스스로 어기지 않도록, 검사하는 프로그램을 만들었습니다.

First I defined what colour has to do in this app. Going through the existing screens, I found the same colour doing two jobs — a control and a state — and that is where the case for dropping the brand colour came from. Then, so I wouldn’t break my own rules, I built a program that checks them.

02 / Context // 두 사용자 · 하나의 흐름// two users, one loop

경기는 매주 정해져 있었지만,
인원은 정해져 있지 않았습니다

Games were fixed every week.
The players weren’t

함께한 개발자가 농구팀을 운영하며 매주 겪던 문제입니다. 체육관과 일정은 정해져 있지만, 인원이 채워져야 경기가 성사됩니다. 그래서 경기 전마다 참석 인원을 세고, 부족한 수를 계산하고, 카카오톡과 커뮤니티에 모집글을 올리고, 댓글로 신청을 받고, 입금을 하나씩 확인했습니다. 매주 일곱 단계를 손으로 거치고 있었습니다.

This was a problem my developer teammate lived every week while running his basketball team. The gym and the schedule were fixed; the players weren’t. Before every game he counted who was coming, worked out the shortfall by hand, posted a recruiting notice to KakaoTalk and community boards, collected sign-ups in the comments, and checked each payment one by one — seven manual steps, every week.

SSP는 이 과정을 하나의 흐름으로 묶습니다. 출석 데이터가 필요한 게스트 수를 예측하고, 예측이 모집글을 자동으로 만들고, 모집 중인 경기는 플레이어의 지도에 뜹니다. 신청 결과는 다시 돌아와 다음 예측을 정확하게 만듭니다. 팀 리드와 플레이어라는 두 사용자가 이 하나의 흐름 양쪽 끝에 있습니다.

SSP folds that into a single loop. Attendance data predicts how many guests are needed, the prediction writes the recruiting post, and open games surface on the player’s map. Sign-ups flow back in and sharpen the next prediction. Team leads and players sit at the two ends of that one loop.

SSP는 두 종류의 사용자가 같은 앱을 씁니다. 팀 리드는 정기전을 열고 출석을 관리하고 모자란 인원만큼 게스트를 모집합니다. 플레이어는 지도에서 오늘 뛸 경기를 찾아 신청합니다. 핵심 가치는 출석 데이터로 게스트 수요를 미리 예측하는 것이고, 발견은 지도 위에서 일어납니다.

Two kinds of user share one app. Team leads open a regular game, track attendance, and recruit exactly as many guests as they are short. Players find a game they can play today on the map and apply. The core value is predicting guest demand from attendance data — and discovery happens on the map.

화면 뼈대(와이어프레임)와 1차 디자인은 이미 있었습니다. 다만 시스템 없이 화면 단위로 만들어져서, 같은 요소가 화면마다 조금씩 다르고 색이 무엇을 뜻하는지 규칙이 없었습니다.

The wireframes and a first design pass already existed. They had been drawn screen by screen without a system, so the same element differed slightly everywhere it appeared, and nothing said what a colour meant.

시스템을 새로 세우면서 첫 질문은 ‘브랜드 색을 무엇으로 할까’가 아니라 ‘이 앱에서 색은 무슨 일을 해야 하는가’였습니다.

Rebuilding it as a system, the first question wasn’t “what should the brand colour be?” but “what does colour have to do in this app?”

지도 기반 서비스에서 사용자는 3초 안에 판단합니다 — 지금 갈 수 있는 경기인가. 그 판단을 색이 담당합니다. 그렇다면 색은 상태를 위해 비워둬야 합니다.

On a map-based service the user decides in three seconds: can I make this game? Colour carries that decision. Which means colour has to be kept free for state.

04 / The Colour Decision // 액센트를 뺀 이유// why the accent went

브랜드 색을 뺀 건 취향이 아니었습니다.
이미 일어나고 있던 충돌을 걷어낸 것입니다

Dropping the accent wasn’t taste.
It cleared a collision that was already happening

기존 화면 18장을 하나씩 세어봤습니다. 색 세 개가 버튼 역할과 상태 표시를 동시에 하고 있었습니다. 네이비는 주 CTA이면서 ‘확정’ 배지였고, 오렌지는 신청 버튼이면서 ‘마감임박’ 배지였고, 파랑은 링크이면서 모집중 핀이었습니다.

I counted the 18 existing screens one by one. Three colours were doing a button’s job and a state’s job at the same time. Navy was the primary CTA and the “confirmed” badge. Orange was the apply button and the “closing soon” badge. Blue was the link and the recruiting pin.

그래서 이런 화면이 나와 있었습니다. ‘신청 마감’이 오렌지 채움 버튼이었습니다 — 누를 수 없는 상태가 화면에서 가장 강한 요소였습니다. ‘현재 부족인원 2명’이 에러 빨강이었습니다 — 아직 일어나지 않은 추정이 이미 잘못된 일처럼 읽혔습니다.

So screens like this had shipped. “Applications closed” was a filled orange button — the one thing you couldn’t press was the loudest element on the screen. “Short by 2 players” was in error red — an estimate that hadn’t happened yet already read as something gone wrong.

브랜드 색을 살리는 쪽도 성실하게 조율해봤습니다. Court Orange를 주 버튼 색으로 놓고 대비를 최대한 끌어올린 안과, 검정만 쓰는 안을 같은 화면으로 나란히 렌더했습니다.

Keeping the brand colour got an honest attempt too. One option put Court Orange on the primary button and pushed its contrast as far as it would go; the other used black alone. Both were rendered on the same screen, side by side.

색을 쓴 안에서는 선택된 필터 칩과 주 버튼이 경기 상태와 같은 색 언어를 씁니다. 검정만 쓴 안에서는 버튼과 필터가 전부 뒤로 물러나고, 색은 경기 상태에만 남습니다.

In the with-colour option, the selected filter chip and the primary button speak the same colour language as the game states. In the black-only option, buttons and filters all step back, and colour is left to game state alone.

다섯 개는 tint(배경) · solid(핀·점) · text(글자) 세 단으로 나뉩니다. 글자와 배경의 밝기 차이를 계산해서, 판단이 필요한 정보는 특히 또렷하게 보이도록 맞췄습니다(웹 접근성 기준 7:1). 그리고 상태를 색으로만 알리지 않습니다. 색을 구별하기 어려운 사람도 알아볼 수 있도록 점이나 글자를 함께 붙입니다.

Each of the five splits into three steps: tint (background), solid (pins and dots) and text. Contrast between text and background was calculated so that anything you have to judge stays sharply legible — 7:1, the web accessibility target. And state is never signalled by colour alone: a dot or a word always comes with it, so people who can’t tell the colours apart can still read it.

05 / Principles // 5
  1. 01

    색은 경기 상태만 말합니다Colour speaks only for game state

    경기 상태는 다섯 개입니다 — 모집중, 마감임박, 마감, 확정, 취소. 화면에서 색이 들어간 요소는 이 다섯 개가 전부입니다. 여섯 번째 색은 만들지 않습니다. 브랜드다움은 색이 아니라 모서리 둥글기, 글꼴, 마스코트, 문장이 만듭니다.

    A game has five states — recruiting, closing soon, closed, confirmed, cancelled. Those five are the only coloured things on screen. There is no sixth colour. Brand character comes from corner radius, type, the mascot and the writing, not from colour.

  2. 02

    누르는 것은 전부 검정과 회색입니다Anything you press is black and grey

    버튼, 필터, 탭처럼 눌러서 무언가를 바꾸는 것에는 색을 쓰지 않습니다. 화면에 색이 보이면 그건 ‘내가 누른 결과’가 아니라 ‘경기가 그런 상태’라는 뜻이어야 합니다.

    Buttons, filters, tabs — anything you press to change something gets no colour. When colour appears, it must mean “the game is in that state”, never “you pressed this”.

  3. 03

    예측은 사실처럼 보이면 안 됩니다A prediction must not look like a fact

    게스트 수요 예측은 추정입니다. 확정된 숫자와 똑같은 무게로 보이면 안 됩니다. 점선 테두리, 확신도 표시, 범위 표기(‘3~5명’)로 ‘이건 아직 제안’이라고 계속 말합니다.

    Guest demand is an estimate. It must never carry the same visual weight as a confirmed number. A dashed border, a confidence indicator and a range (“3–5 guests”) keep saying: this is still a suggestion.

  4. 04

    지도 위에서는 색보다 모양입니다On the map, shape beats colour

    지도는 우리가 만든 화면이 아닙니다. 무엇이 깔릴지 모르는 배경 위에서 색만으로 구별하려 하면 실패합니다. 그래서 모양으로 먼저 구별하고, 색은 거들게 했습니다.

    The map isn’t our screen. Telling things apart by colour alone, on a background we don’t control, fails. So shape does the separating and colour only assists.

  5. 05

    모집글은 앱 밖으로 나갑니다The recruiting post leaves the app

    자동으로 만들어진 모집글은 카카오톡과 커뮤니티로 나갑니다. 우리가 손댈 수 없는 곳에서 첫인상을 만드는 화면이라, 따로 설계했습니다.

    Auto-generated recruiting posts go out to KakaoTalk and community boards. It’s the screen that forms a first impression somewhere we can’t touch, so it was designed separately.

06 / Foundations // 색 53 · 사이즈 50 · 닫힌 집합// 53 colours · 50 sizes · a closed set

결정이 끝난 뒤 실제로 만든 것들입니다. 도메인마다 값과, 그 값을 그렇게 정한 이유를 함께 적었습니다.

What actually got built once the decisions were made. Each domain lists its values, and the reason those values are what they are.

색마다 이름을 붙였습니다. #151E28 대신 surface-inverse처럼요. 이름이 없으면 이 색을 어디에 써야 하는지 아무도 알 수 없습니다. 그러면 시스템이 아니라 그냥 색 모음이 됩니다.

Every colour has a name — surface-inverse rather than #151E28. Without a name nobody knows where the colour is supposed to go, and what you have is a pile of colours, not a system.

Colour // 53 tokens · 유채색은 status 5색 파생만// 53 tokens · chromatic only in the five status colours
왜Why

조작에 쓸 색을 아예 만들지 않았습니다. 화면에 색이 보이면 그건 언제나 경기 상태입니다.

No colour was ever made for controls. If you see colour on screen, it always means game state.

규칙Rule

목록 밖의 값은 쓸 수 없습니다. 꼭 예외가 필요하면 코드에 ssp-allow(규칙): 사유 형식으로 이유를 적어야 통과합니다.

Values outside the list can’t be used. An exception passes only if the reason is written into the code as ssp-allow(rule): reason.

Typography // Pretendard · 13 roles · 10 sizes
왜Why

13은 크기가 아니라 역할의 수입니다. 크기는 10개뿐이고, 한 크기가 두 역할을 맡을 때는 무게와 행간이 나눕니다 — 읽는 글과 누르는 글은 같은 15px이어도 같은 글이 아닙니다.

13 counts roles, not sizes. There are only 10 sizes; where one size carries two roles, weight and leading separate them — body and label are not the same text at 15px.

규칙Rule

스케일에 없는 크기는 쓰지 않습니다.

No size that isn’t on the scale.

Spacing // base 4 · 13 steps + 0
왜Why

4의 배수로만 잡았습니다. 그래야 ‘마크 높이의 1/4’ 같은 규칙의 결과가 항상 스케일 위에 떨어집니다 — 16→4, 24→6, 32→8, 64→16.

Everything is a multiple of 4, so a rule like “a quarter of the mark height” always lands on the scale — 16→4, 24→6, 32→8, 64→16.

규칙Rule

4로 나누어떨어지지 않는 여백은 쓰지 않습니다.

No spacing that isn’t divisible by 4.

Radius // badge 6 · thumb 10 · button 12 · card 16 · sheet 20 · chip full
왜Why

브랜드 색을 빼고 나니 화면이 차가워 보였습니다. 그 온기를 모서리 둥글기가 대신 냅니다. 스케일에서 통상값보다 한 칸씩 위로 올렸습니다 — badge 4→6, button 10→12, card 12→16, sheet 16→20. 취향이 아니라 무액센트가 만든 빚을 갚는 자리입니다.

Dropping the brand colour left the screens looking cold. Radius carries that warmth instead. Every component sits one step above its conventional value — badge 4→6, button 10→12, card 12→16, sheet 16→20. Not taste: paying back what dropping the accent cost.

규칙Rule

부품마다 반경을 고정합니다. 같은 부품이 화면마다 다른 반경을 갖지 않습니다.

Each component owns one radius. The same part never changes radius between screens.

내가 누르는 필터 칩은 알약, 경기 상태를 말하는 배지는 각진 6 — 조작과 상태를 색으로 못 가르니 형태가 가름 The filter chip you press is a pill; the badge that reports state is a squared 6 — with colour off the table, shape does the separating

Density // compact 44 / comfortable 48
왜Why

팀 리드 화면은 한 번에 봐야 할 정보가 많고, 플레이어는 지도 위에서 손가락으로 누릅니다. 버튼 높이와 ‘최소한 이만큼은 되어야 눌리는 크기’를 같은 값으로 묶어서, 높이만 정하면 누르기 편한 크기가 저절로 따라오게 했습니다.

Team leads hold a lot on one screen; players press with a thumb on a map. Control height and minimum touch target are locked to the same value, so setting the height makes the tappable size follow automatically.

규칙Rule

두 모드 밖의 컨트롤 높이는 만들지 않습니다.

No control height outside the two modes.

Components // 26 groups · 92 variants
왜Why

화면을 만들 때 여기 없는 것은 만들지 않습니다. 새 상태가 필요하면 그건 새 컴포넌트가 아니라 기존 것의 변형이거나, 잘못된 상태 모델입니다.

Building a screen means building nothing that isn’t already here. A state you need is either a variant of something existing, or a sign the state model is wrong.

규칙Rule

화면 12장을 조립하며 새로 만든 컴포넌트는 0개였습니다.

Zero new components across all 12 screens.

MapPin — 형태로 구별합니다MapPin — tell it apart by shape.

네이버 지도 위에는 카페, 편의점 같은 동그란 아이콘이 25개 넘게 깔려 있습니다. 우리 핀도 동그라미면 그 사이에 묻힙니다. 그래서 아래가 뾰족한 물방울 모양(36×44)으로 만들었습니다. 뾰족한 끝이 경기 장소를 정확히 가리키고, 흰색 테두리 2px가 지도 배경에서 핀을 떼어냅니다. 그림자는 우리 시스템이 금지한 효과라 쓰지 않았습니다.

A Naver map is already covered with 25-plus round icons — cafés, convenience stores. A round pin of ours would disappear among them. So the pin is a teardrop, 36×44, pointed at the bottom: the point marks the exact court, and a 2px white outline lifts it off the map. No drop shadow — shadows are on the system’s banned list.

PredictionCard — 확신을 눈에 보이게 합니다PredictionCard — make the confidence visible.

2px 점선 테두리로 ‘확정 아님’을 계속 말합니다. 누적 경기 수에 따라 확신이 높으면 단일값(‘게스트 4명’), 낮으면 범위(‘게스트 3~5명’)로 바뀌고 점 3개짜리 인디케이터가 근거의 두께를 보여줍니다. 여기에는 경기 상태 색을 쓰지 않습니다. 상태 색은 확정된 사실에만 쓰는 색인데, 예측은 아직 사실이 아니기 때문입니다.

A 2px dashed border keeps saying “not confirmed”. As games accumulate, high confidence reads as a single number (“4 guests”) and low confidence as a range (“3–5 guests”), with a three-dot indicator showing how much evidence sits behind it. State colours are not used here. Those colours are for confirmed facts, and a prediction is not a fact yet.

출석 응답 — 색을 쓰지 않기로 했습니다Attendance replies — the decision to use no colour.

참석 · 불참 · 미정 · 미응답. 여기에 색을 주면 색이 아홉 개가 됩니다. 시스템이 시험당한 순간이었고, 색을 전혀 쓰지 않는 쪽을 택했습니다. status 색은 ‘지금 갈 수 있나’를 3초에 판단하는 용도인데, 출석 확인은 앉아서 하는 검토라 같은 채널을 쓸 이유가 없습니다. ‘게스트가 필요하다’는 신호는 PredictionCard가 이미 담당합니다.

Going, not going, undecided, no answer. Give those four a colour each and the palette has nine. This was the moment the system got tested, and the answer was no colour at all. Status colour exists so you can judge “can I make this?” in three seconds; checking attendance is a seated review, with no reason to borrow the same channel. The signal that says “we need guests” is already the PredictionCard’s job.

왜Why

숫자가 아니라 규칙을 적습니다. ‘PENGUIN은 SHOOT 폭에 정렬한다’로 적어두면 폰트를 바꿔도 정렬이 유지되고, ‘+50.5%’라고 적어두면 크기만 바꿔도 깨집니다.

Write the rule, not the number. “PENGUIN aligns to the width of SHOOT” survives a font change; “+50.5% tracking” breaks the moment the size changes.

Clear Space는 마크 높이의 1/4입니다. 결과가 항상 스페이싱 토큰 위에 떨어집니다.

07 / Enforcement // 검증 스크립트// the validator

규칙을 스크립트로 만들었습니다

Turning the rules into a script

규칙을 문서에만 적어두면 지켜지지 않습니다. 저부터 그랬습니다. 그래서 시스템을 다시 만드는 내내, 제가 정한 규칙을 제가 어기고 있지 않은지 검사하는 프로그램을 돌렸습니다.

A rule written only into a document doesn’t get followed. I was the first to prove that. So while rebuilding the system, I kept a program running that checked whether I was breaking my own rules.

쓰면 안 되는 것들을 자동으로 찾아냅니다. 색이 번지는 효과, 빛나는 효과, 반투명 유리처럼 보이는 카드, 목록에 없는 색과 크기, 그리고 채우지 않고 남겨둔 임시 글자까지요.

It finds what isn’t allowed: colours that bleed into each other, glow effects, cards that look like frosted glass, any colour or size that isn’t on the list, and placeholder text left unfilled.

이 스크립트가 가장 많이 잡은 건 제 실수였습니다.

What it caught most was my own work.

@font-face의 font-weight: 100 900, 포커스 링에 쓴 오프셋 0 그림자, 스케일에 없는 max-width: 640px, margin-top: 5px — 전부 제가 쓴 것이고 스크립트가 먼저 발견했습니다.

A font-weight: 100 900 in an @font-face, a zero-offset shadow used as a focus ring, a max-width: 640px that isn’t on the scale, a margin-top: 5px — all mine, and the script found every one of them before I did.

08 / Handoff // HTML/CSS → html.to.design

Figma로 옮기는 법을 바꿨습니다

Changing how it got into Figma

처음에는 Figma Make로 만들 계획이었습니다. 프롬프트를 정교하게 써서 넣었더니 팔레트 목업을 그려버렸습니다. 실패 원인을 뜯어보니 도구를 잘못 이해한 것이었습니다 — Figma Make는 프롬프트로 앱을 만드는 도구지 Figma 스타일과 변수를 만드는 도구가 아닙니다. 제 프롬프트는 구조적으로 불가능한 것을 요구하고 있었습니다.

The plan was to build it in Figma Make. I wrote a careful prompt, fed it in, and got a mockup of a palette back. Taking the failure apart, the fault was in how I understood the tool — Figma Make builds apps from prompts; it doesn’t build Figma styles and variables. My prompt was asking for something structurally impossible.

그래서 경로를 바꿨습니다. 컴포넌트를 HTML/CSS로 실제로 짓고 html.to.design으로 들여오는 방식입니다. 그림이 아니라 진짜 마크업이라 검증 스크립트를 그대로 돌릴 수 있고, 시스템이 바뀌면 다시 빌드하면 됩니다.

So the route changed: build the components in real HTML/CSS and import them through html.to.design. Because they are markup rather than drawings, the validator runs on them unchanged — and when the system moves, you rebuild.

여기서 파일럿을 먼저 돌린 게 결정적이었습니다. 8장을 한꺼번에 넣기 전에 2장만 넣어봤는데, 글자 크기 12px이 card-gap(카드 사이 간격) 값에 잘못 연결돼 있었습니다. 카드 간격을 바꾸면 글자 크기까지 같이 변하는 상태였습니다.

Running a pilot first is what saved it. Before pushing all eight screens through, I sent two — and a 12px font size had been wired to card-gap — the value for the space between cards. Change the card spacing and the text size changed with it.

원인은 제 쪽이었습니다. 타입 스케일을 CSS 변수로 노출한 적이 없어서, 도구가 12라는 값을 가진 변수를 찾다가 간격 변수를 집은 것입니다. fs-* lh-* fw-* 26개를 추가하고 CSS 135곳을 바꿔 해결했고, ‘값 하나당 변수 하나’라는 규칙을 세워 중복 변수 24개를 걷어냈습니다.

The cause was on my side. I had never exposed the type scale as CSS variables, so the tool went looking for a variable holding the value 12 and grabbed a spacing one. Adding 26 fs-*, lh-* and fw-* variables and changing 135 places in the CSS fixed it — and one rule, one variable per value, cleared out 24 duplicates.

프롬프트를 계속 다듬는 것보다, 도구를 잘못 골랐다고 빨리 인정하는 편이 빨랐습니다.

Admitting I had picked the wrong tool was faster than another round of refining the prompt.

11 / What I Learned // 2

주장을 증명하려면 반대쪽 안을 제대로 만들어야 합니다Proving a claim means building the other side properly

브랜드 색을 빼자고 하려면, 색을 살린 안도 대비까지 맞춰 제대로 만들어야 합니다. 그런데 더 센 게 따로 있었습니다. 처음엔 ‘색을 얹으면 충돌할 것이다’라고 예상하고 그림을 만들었는데, 기존 화면 18장을 다시 세어보니 이미 충돌하고 있었습니다. 없는 시안을 두고 하는 주장보다, 이미 그려져 있던 화면을 보여주는 쪽이 반박할 수 없습니다.

To argue for dropping the brand colour, the version that keeps it has to be built properly, contrast and all. But something else turned out to be stronger. The first comparison was a prediction — put colour on and it will collide. Counting the 18 existing screens again changed the claim: it was already colliding. Showing a screen that had actually been drawn is harder to argue with than a case about a mockup that never existed.

규칙은 지킬 수 있게 만들어야 규칙입니다A rule is only a rule if it can be kept

문서에 적어둔 금지 항목은 지켜지지 않았습니다. 스크립트로 만들고 나서야, 제가 낸 실수까지 포함해 실제로 걸리기 시작했습니다.

The prohibitions written into a document were not followed. Only once they were a script did things actually start getting caught — my own mistakes included.

이 프로젝트는 화면이 아니라 시스템을 설계하는 법을 가르쳐줬습니다. 두 사용자의 니즈를 하나의 흐름으로 연결하는 일 — 그리고 그것을 첫날부터 개발자와 함께 하는 일은 디자인 방식 자체를 바꿨습니다. 모든 결정이 구현 가능성의 검증을 통과해야 했기 때문입니다. 검증은 다음 챕터이고, 제품은 측정될 준비가 되어 있습니다.

This project taught me to design a system, not screens. Connecting two users' needs into a single flow — and doing it alongside a developer from day one — changed how I design, because every decision had to survive a feasibility check. Validation is the next chapter; the product is ready to be measured.
