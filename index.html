Shoot Shoot Penguin
Design System

Shoot Shoot Penguin의 초기 화면을 검토하며, 반복 요소의 스타일과
색의 의미가 화면마다 달라지는 문제를 발견했습니다.
조작 요소와 경기 상태의 표현을 분리하고, 토큰과 컴포넌트를 정리해
두 사용자 화면에 적용할 공통 기준을 만들었습니다.

Reviewing the first screens of Shoot Shoot Penguin, I found that repeated elements were styled differently from screen to screen, and that colour meant something different in each one.
Separating how controls and game state are expressed, then settling the tokens and components, gave one standard both sides of the app could be built on.

01 / Summary
문제Problem

화면별로 제작한 초기 UI에는 반복 요소의 스타일 차이가 있었고, 같은 색이 버튼과 경기 상태를 함께 나타내고 있었습니다.

The first UI was built screen by screen, so repeated elements were styled differently, and one colour stood for a button and a game state at the same time.

접근Approach

색의 역할을 분리하고, 타이포그래피 · 간격 · 컴포넌트를 공통 규칙으로 정리했습니다. 예측 정보는 확정 정보와 구별되도록 표현했습니다.

Colour’s roles were separated, and typography, spacing and components were settled into shared rules. Predicted information was expressed so that it reads as distinct from confirmed information.

산출물Deliverables

디자인 토큰, 컴포넌트 26그룹, 브랜드 자산과 화면 적용 시안을 제작했습니다. HTML/CSS에서 규칙 위반을 확인하는 검사 프로그램도 구성했습니다.

Design tokens, 26 component groups, brand assets and applied screen mockups. Plus a checker that finds rule violations in the HTML and CSS.

02 / Context

두 사용자의 다른 작업을
하나의 UI 기준으로 연결했습니다

Two users, two different jobs,
joined by one UI standard

Shoot Shoot Penguin은 팀 리드의 게스트 모집과 플레이어의 경기 탐색을 연결하는 농구 앱입니다. 팀 리드는 출석과 모집 인원을 관리하고, 플레이어는 지도에서 참여할 경기를 찾습니다.

Shoot Shoot Penguin is a basketball app that joins a team lead’s guest recruiting to a player’s search for a game. Team leads manage attendance and how many guests they need; players find a game to join on a map.

같은 경기 정보도 관리하는 화면에서는 비교하기 쉽게, 탐색 화면에서는 빠르게 구별되게 보여야 합니다. 이번 시스템은 공통 컴포넌트를 기반으로 각 작업에 맞는 정보 위계와 상태 표현을 정의했습니다.

The same game information has to be easy to compare on a screen you manage from, and quick to tell apart on a screen you search from. This system defines the information hierarchy and the state expression each job needs, on top of one shared set of components.

03 / Why a System

화면마다 달랐던 표현을
공통 규칙으로 정리했습니다

Expression that differed screen by screen,
settled into shared rules

화면 뼈대(와이어프레임)와 1차 UI는 있었지만, 반복 요소의 스타일과 색상 기준이 화면마다 달랐습니다. 요소를 수정할 때마다 개별 화면을 확인해야 했습니다.

The wireframes and a first pass at the UI existed, but repeated elements were styled differently from screen to screen and nothing set a standard for colour. Changing one element meant checking every screen it appeared on.

기존 화면을 검토해 반복 요소와 상태 표현을 분류하고, 공통 토큰과 컴포넌트를 정의했습니다. 먼저 버튼과 경기 상태에 혼용되던 색상의 역할을 분리했습니다.

Reviewing those screens, I sorted the repeated elements and the ways state was expressed, then defined shared tokens and components. The first thing separated was colour’s role, which buttons and game states had been sharing.

04 / The Colour Decision

색상 역할을 분리해
경기 상태를 구분했습니다

Colour’s roles separated,
so game state reads on its own

초기 화면에서는 오렌지가 신청 버튼과 마감임박 배지에 함께 사용되었습니다.
신청이 종료된 요소도 강한 채움색으로 표시되어, 행동 유도와 경기 상태가 구분되지 않았습니다.

In the first screens, orange was used for the apply button and for the closing-soon badge alike. Elements whose applications had already closed were filled just as strongly, so a call to action and a game state could not be told apart.

이를 개선하기 위해 주요 조작 요소에는 무채색을, 경기 상태에는 구분 색상을 적용했습니다.
색상은 상태 정보에 집중해 버튼과 상태가 서로 다른 신호를 전달하도록 했습니다.

To fix it, the main controls took neutral colour and game states took distinguishing colour. Colour concentrates on state information, so a button and a state carry different signals.

유채색 버튼과 무채색 버튼을 비교한 결과, 무채색 버튼은 경기 상태 색상과 충돌하지 않았습니다.
조작 요소와 상태 정보가 분리되면서 정보 위계도 명확해졌습니다.

Comparing a coloured button with a neutral one, the neutral button did not collide with the game state colours. With controls separated from state information, the information hierarchy became clear as well.

다섯 가지 상태색을 배경(tint) · 핀과 점(solid) · 텍스트(text)로 구분했습니다.
판단에 필요한 텍스트는 배경과 7:1 이상의 명도 대비를 확보하고, 상태명과 표시를
함께 사용해 색상에만 의존하지 않도록 설계했습니다.

Each of the five state colours is split into a background (tint), a pin or dot (solid) and text.
Text that carries a decision holds at least 7:1 contrast against its background, and the state’s name and marker travel with it, so nothing depends on colour alone.

06 / Foundations

반복되는 시각적 결정을
토큰으로 정리했습니다

The visual decisions that repeat,
settled into tokens

색상, 타이포그래피, 간격, 모서리 반경을 공통 값으로 정의했습니다. 각 값에는 사용 목적을 함께 기록해,
화면을 추가하거나 수정할 때 같은 기준을 적용할 수 있도록 했습니다.

Colour, typography, spacing and corner radius are defined as shared values. Each value carries a note on what it is for, so the same standard applies when a screen is added or changed.

Colour

배경 · 텍스트 · 테두리 · 경기 상태 등 역할에 따라 사용할 색을 구분했습니다.

Colours are separated by the job they do — background, text, border and game state.

Typography

제목 · 본문 · 레이블의 위계를 크기, 굵기, 행간의 조합으로 정의했습니다.

The hierarchy of headings, body and labels is defined by a combination of size, weight and leading.

Spacing & shape

반복되는 여백과 컴포넌트별 모서리 반경을 정리해 화면 간 차이를 줄였습니다.

Recurring spacing and each component’s corner radius were settled, so screens differ less from one another.

Density

정보를 모아 보는 관리 화면과 지도에서 조작하는 탐색 화면에 맞춰 두 가지 컨트롤 크기를 정의했습니다.

Two control sizes: one for the management screens where information is gathered, one for the map screens worked by hand.

07 / Components
왜Why

화면을 만들 때 여기 없는 것은 만들지 않습니다. 새 상태가 필요하면 그건 새 컴포넌트가 아니라 기존 것의 변형이거나, 잘못된 상태 모델입니다.

Building a screen means building nothing that isn’t already here. A state you need is either a variant of something existing, or a sign the state model is wrong.

규칙Rule

화면 12장을 조립하며 새로 만든 컴포넌트는 0개였습니다.

Zero new components across all 12 screens.

MapPin — 형태로 구별합니다MapPin — tell it apart by shape.

네이버 지도 위에는 카페, 편의점 같은 동그란 아이콘이 25개 넘게 깔려 있습니다. 우리 핀도 동그라미면 그 사이에 묻힙니다. 그래서 아래가 뾰족한 물방울 모양(36×44)으로 만들었습니다. 뾰족한 끝이 경기 장소를 정확히 가리키고, 흰색 테두리 2px가 지도 배경에서 핀을 떼어냅니다. 그림자는 우리 시스템이 금지한 효과라 쓰지 않았습니다.

A Naver map is already covered with 25-plus round icons — cafés, convenience stores. A round pin of ours would disappear among them. So the pin is a teardrop, 36×44, pointed at the bottom: the point marks the exact court, and a 2px white outline lifts it off the map. No drop shadow — shadows are on the system’s banned list.

PredictionCard — 확신을 눈에 보이게 합니다PredictionCard — make the confidence visible.

2px 점선 테두리로 ‘확정 아님’을 계속 말합니다. 누적 경기 수에 따라 확신이 높으면 단일값(‘게스트 4명’), 낮으면 범위(‘게스트 3~5명’)로 바뀌고 점 3개짜리 인디케이터가 근거의 두께를 보여줍니다. 여기에는 경기 상태 색을 쓰지 않습니다. 상태 색은 확정된 사실에만 쓰는 색인데, 예측은 아직 사실이 아니기 때문입니다.

A 2px dashed border keeps saying “not confirmed”. As games accumulate, high confidence reads as a single number (“4 guests”) and low confidence as a range (“3–5 guests”), with a three-dot indicator showing how much evidence sits behind it. State colours are not used here. Those colours are for confirmed facts, and a prediction is not a fact yet.

출석 응답 — 색을 쓰지 않기로 했습니다Attendance replies — the decision to use no colour.

참석 · 불참 · 미정 · 미응답. 여기에 색을 주면 색이 아홉 개가 됩니다. 시스템이 시험당한 순간이었고, 색을 전혀 쓰지 않는 쪽을 택했습니다. status 색은 ‘지금 갈 수 있나’를 3초에 판단하는 용도인데, 출석 확인은 앉아서 하는 검토라 같은 채널을 쓸 이유가 없습니다. ‘게스트가 필요하다’는 신호는 PredictionCard가 이미 담당합니다.

Going, not going, undecided, no answer. Give those four a colour each and the palette has nine. This was the moment the system got tested, and the answer was no colour at all. Status colour exists so you can judge “can I make this?” in three seconds; checking attendance is a seated review, with no reason to borrow the same channel. The signal that says “we need guests” is already the PredictionCard’s job.

08 / Brand
왜Why

숫자가 아니라 규칙을 적습니다. ‘PENGUIN은 SHOOT 폭에 정렬한다’로 적어두면 폰트를 바꿔도 정렬이 유지되고, ‘+50.5%’라고 적어두면 크기만 바꿔도 깨집니다.

Write the rule, not the number. “PENGUIN aligns to the width of SHOOT” survives a font change; “+50.5% tracking” breaks the moment the size changes.

규칙Rule

Clear Space는 마크 높이의 1/4입니다. 결과가 항상 스페이싱 토큰 위에 떨어집니다.

Clear space is a quarter of the mark height, so the result always lands on a spacing token.

Pretendard에서 Poppins로 교체했을 때 자간이 52.7%에서 50.5%로 자동 재계산되면서 정렬이 유지됨 Swapping Pretendard for Poppins recalculated the tracking from 52.7% to 50.5% on its own, and the alignment held

09 / Enforcement

규칙을 스크립트로 만들었습니다

Turning the rules into a script

규칙을 문서에만 적어두면 지켜지지 않습니다. 저부터 그랬습니다. 그래서 시스템을 다시 만드는 내내, 제가 정한 규칙을 제가 어기고 있지 않은지 검사하는 프로그램을 돌렸습니다.

A rule written only into a document doesn’t get followed. I was the first to prove that. So while rebuilding the system, I kept a program running that checked whether I was breaking my own rules.

쓰면 안 되는 것들을 자동으로 찾아냅니다. 색이 번지는 효과, 빛나는 효과, 반투명 유리처럼 보이는 카드, 목록에 없는 색과 크기, 그리고 채우지 않고 남겨둔 임시 글자까지요.

It finds what isn’t allowed: colours that bleed into each other, glow effects, cards that look like frosted glass, any colour or size that isn’t on the list, and placeholder text left unfilled.

이 스크립트가 가장 많이 잡은 건 제 실수였습니다.

What it caught most was my own work.

@font-face의 font-weight: 100 900, 포커스 링에 쓴 오프셋 0 그림자, 스케일에 없는 max-width: 640px, margin-top: 5px — 전부 제가 쓴 것이고 스크립트가 먼저 발견했습니다.

A font-weight: 100 900 in an @font-face, a zero-offset shadow used as a focus ring, a max-width: 640px that isn’t on the scale, a margin-top: 5px — all mine, and the script found every one of them before I did.

10 / Handoff

Figma로 옮기는 법을 바꿨습니다

Changing how it got into Figma

처음에는 Figma Make로 만들 계획이었습니다. 프롬프트를 정교하게 써서 넣었더니 팔레트 목업을 그려버렸습니다. 실패 원인을 뜯어보니 도구를 잘못 이해한 것이었습니다 — Figma Make는 프롬프트로 앱을 만드는 도구지 Figma 스타일과 변수를 만드는 도구가 아닙니다. 제 프롬프트는 구조적으로 불가능한 것을 요구하고 있었습니다.

The plan was to build it in Figma Make. I wrote a careful prompt, fed it in, and got a mockup of a palette back. Taking the failure apart, the fault was in how I understood the tool — Figma Make builds apps from prompts; it doesn’t build Figma styles and variables. My prompt was asking for something structurally impossible.

그래서 경로를 바꿨습니다. 컴포넌트를 HTML/CSS로 실제로 짓고 html.to.design으로 들여오는 방식입니다. 그림이 아니라 진짜 마크업이라 검증 스크립트를 그대로 돌릴 수 있고, 시스템이 바뀌면 다시 빌드하면 됩니다.

So the route changed: build the components in real HTML/CSS and import them through html.to.design. Because they are markup rather than drawings, the validator runs on them unchanged — and when the system moves, you rebuild.

여기서 파일럿을 먼저 돌린 게 결정적이었습니다. 8장을 한꺼번에 넣기 전에 2장만 넣어봤는데, 글자 크기 12px이 card-gap(카드 사이 간격) 값에 잘못 연결돼 있었습니다. 카드 간격을 바꾸면 글자 크기까지 같이 변하는 상태였습니다.

Running a pilot first is what saved it. Before pushing all eight screens through, I sent two — and a 12px font size had been wired to card-gap — the value for the space between cards. Change the card spacing and the text size changed with it.

원인은 제 쪽이었습니다. 타입 스케일을 CSS 변수로 노출한 적이 없어서, 도구가 12라는 값을 가진 변수를 찾다가 간격 변수를 집은 것입니다. fs-* lh-* fw-* 26개를 추가하고 CSS 135곳을 바꿔 해결했고, ‘값 하나당 변수 하나’라는 규칙을 세워 중복 변수 24개를 걷어냈습니다.

The cause was on my side. I had never exposed the type scale as CSS variables, so the tool went looking for a variable holding the value 12 and grabbed a spacing one. Adding 26 fs-*, lh-* and fw-* variables and changing 135 places in the CSS fixed it — and one rule, one variable per value, cleared out 24 duplicates.

프롬프트를 계속 다듬는 것보다, 도구를 잘못 골랐다고 빨리 인정하는 편이 빨랐습니다.

Admitting I had picked the wrong tool was faster than another round of refining the prompt.

13 / What I Learned

주장을 증명하려면 반대쪽 안을 제대로 만들어야 합니다Proving a claim means building the other side properly

브랜드 색을 빼자고 하려면, 색을 살린 안도 대비까지 맞춰 제대로 만들어야 합니다. 그런데 더 센 게 따로 있었습니다. 처음엔 ‘색을 얹으면 충돌할 것이다’라고 예상하고 그림을 만들었는데, 기존 화면 18장을 다시 세어보니 이미 충돌하고 있었습니다. 없는 시안을 두고 하는 주장보다, 이미 그려져 있던 화면을 보여주는 쪽이 반박할 수 없습니다.

To argue for dropping the brand colour, the version that keeps it has to be built properly, contrast and all. But something else turned out to be stronger. The first comparison was a prediction — put colour on and it will collide. Counting the 18 existing screens again changed the claim: it was already colliding. Showing a screen that had actually been drawn is harder to argue with than a case about a mockup that never existed.

규칙은 지킬 수 있게 만들어야 규칙입니다A rule is only a rule if it can be kept

문서에 적어둔 금지 항목은 지켜지지 않았습니다. 스크립트로 만들고 나서야, 제가 낸 실수까지 포함해 실제로 걸리기 시작했습니다.

The prohibitions written into a document were not followed. Only once they were a script did things actually start getting caught — my own mistakes included.

회고 Reflection

이 프로젝트는 화면이 아니라 시스템을 설계하는 법을 가르쳐줬습니다. 두 사용자의 니즈를 하나의 흐름으로 연결하는 일 — 그리고 그것을 첫날부터 개발자와 함께 하는 일은 디자인 방식 자체를 바꿨습니다. 모든 결정이 구현 가능성의 검증을 통과해야 했기 때문입니다. 검증은 다음 챕터이고, 제품은 측정될 준비가 되어 있습니다.

This project taught me to design a system, not screens. Connecting two users' needs into a single flow — and doing it alongside a developer from day one — changed how I design, because every decision had to survive a feasibility check. Validation is the next chapter; the product is ready to be measured.
